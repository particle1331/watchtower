The user wants to check their answer to a course problem against the stored solutions.

1. Resolve the course:
   - If `$1` matches a directory under `courses/` (e.g. `cla`, `mlops`), that is the course and the remaining arguments locate the problem.
   - Otherwise infer the course from context: which course notebook the user is currently working in, or the most recently discussed course. If the course is still ambiguous, ask the user which course before proceeding.
   Read `courses/<course>/problems.json` (the solutions file). If it does not exist, say so and stop — the file is generated by merging the per-chapter segments.
2. Resolve the problem. Accept any of these forms:
   - `/check-answer cla 7.3 <answer>` — `$1` is the course, `$2` is `chapter.problem` (e.g. `7.3` = problem 3 of chapter 7)
   - `/check-answer 07 3 <answer>` — `$1` is the chapter (number, stem like `07-projection-and-orthogonalization`, or fuzzy title match), `$2` is the problem number
   - `/check-answer 07-3 <answer>` — `$1` is a full problem id
   The user's answer is everything in `$ARGUMENTS` after the locator arguments. If it is empty, ask the user to paste their answer (text, math, or code) and stop — do not reveal the solution yet.
3. Grade, don't dump:
   - For problems with `solution.checks` (numeric expected values): extract the user's numeric answer(s) and compare against `expected` within `tolerance`. State pass/fail per check.
   - If the user's answer is code: run it and compare its output against the checks.
   - For theory problems: compare the user's reasoning against `solution.text` and judge correctness, noting missing or wrong steps.
4. Report: a verdict per part, what is right, what is wrong, and the reference answer (`solution.answer` / `solution.text`). Only reveal the full worked solution after grading the user's answer.
